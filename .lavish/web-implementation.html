EviFinance · web Planning only · nothing built or run

Can EviFinance run on the web?

Yes. The app was built so that most of it is plain TypeScript, and the backend already accepts browser requests. The real question is how much of the phone UI you want to keep on a desktop screen.

Decided: Option 2, admin-first. Run the existing app in the browser with react-native-web, then give the 5 admin screens that matter a real desktop layout. About 3,700 lines new or changed (≈17% of the 21k in src/), in roughly 55 files, reusing the mobile screens and UI kit rather than redesigning them, no change to the phone build. Do a one-day spike first to confirm the animation library.

Three ways to do it

Bars show how much of the result is reused as it is (green), edited in place (amber) or written new (red).

Reused as isEditedNew code

1 · Same app, in a browser

Quickest

react-native-web, phone layout centred in a column. Installable on iPhones as a home-screen app.

  • ~1,900 lines new or changed
  • ~35 files, mostly new *.web.ts stand-ins
  • Feasibility: high
  • Feels like a phone app on a big screen. Fine for employees on any phone, poor for an admin at a desk.

2 · Browser app + desktop layout

Recommended

Option 1, plus a sidebar and master-detail layouts on wide screens. Phones keep today's layout.

  • ~3,700 lines new or changed (range 3,100 – 4,600)
  • ~55 files (35 new, 20 edited)
  • Feasibility: high after the spike
  • One codebase, one set of fixes. Admin and employee both get web.

3 · Separate admin console

Most work

A new React + Vite site for admins only, sharing types, formatting and the API client through a shared package.

  • ~10,000 new lines, +~25 app files edited to move shared code
  • ~24 admin screens rebuilt as tables and forms
  • Feasibility: high, but long
  • Best desktop result. Two UIs to keep in step forever, and employees get nothing.

Stop points

  • After 1 – 4, 7 (~1,900 lines): Option 1 is done. Employees can use the app in any browser and install it on an iPhone.
  • After 5: admins get the sidebar and wide cards, but still single-column screens.
  • After 6: the full Option 2. Package 6 can be done one screen at a time, so it can stop whenever it is good enough.

Backend, security and hosting

Token storage + PIN unlock

A browser has no keychain. Proposal: the token is stored encrypted with a key made from a PIN (Web Crypto, PBKDF2 + AES-GCM), so a closed tab asks for the PIN, not the password. Use 6 digits and wipe after 5 wrong tries. Caveat: someone who copies the stored data can guess a PIN offline, so this stops casual access, not a determined attacker. Stronger option: a passkey (WebAuthn, fingerprint or Windows Hello), similar effort.

CORS is wide open

app.use(cors()) allows every origin. Restrict it to the web origin before it goes live. The Bearer-token scheme means no CSRF protection is needed.

Hosting is separate

The web build is a static folder (HTML, JS, assets) with nothing server-side. Any static host works, and the backend repo gets no web files. Because it is a different origin, the CORS allow-list is required, not optional.

Decisions so far

Option 2 · go

Confirmed. Admin-first: the desktop layouts (package 6) come before anything employee-specific, and the employee screens simply work in the phone layout.

Hosting · outside the backend

No web files in the backend repo. The build is a static folder you can put on any static host or domain later. The backend only gets a CORS allow-list for that origin (~5 lines, no files).

Session · PIN unlock (proposed)

Yes, this works: a tab-closing session plus a PIN, like the phone quick unlock. How it works is in the Token storage box above. It adds ~250 lines (package 8), and a PIN is weaker than the phone keychain.

Branch · new, from main

The revamp is merged, so web starts on a new branch off main (feat/web). The spike lives there too.

Next step: a one-day spike on feat/web (new, from main): package 1 plus the three riskiest screens (Home, a list, the payment sheet), built off this machine, with an admin-first order for everything after. It settles the reanimated question and turns the 3,000 – 4,500 range into a firmer number before anything bigger is committed.
