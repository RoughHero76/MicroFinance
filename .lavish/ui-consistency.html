Localization with server messages: why it doesn't break

Two owners, no overlapThe app owns every label, button and screen text (app/i18n/en.json, hi.json). The server owns only result messages: errors, successes and notification text (backend/src/i18n/en.json, hi.json). The same key never lives in both places.
Every request says the languageThe app sends Accept-Language: hi or en (the current setting). Switching language in Settings takes effect on the next request, and cached notifications are re-fetched so they show in the new language.
Safe fallbacksIf a Hindi message is missing on the server, it sends English (never an empty string). Old app versions that don't send the header get English, as today. With no internet, the app uses its own text, because there's no server reply.
Same words everywhereA shared glossary (for example installment = "किस्त", penalty = "जुर्माना", collector = "वसूलीकर्ता") is copied into both repos by a small script, so the app and server never use different Hindi words for the same thing. Amounts and dates are formatted per language on both sides (Intl hi-IN / en-IN).

Pick a toast style

"Can we even undo?" I checked the backend. Approve: yes, safely. approveRepaymentHistory only changes the status from Pending to Approved; the money was already applied to the schedule when the payment was recorded. Undo just sets it back to Pending, and no amounts move. This needs a tiny endpoint, POST /admin/loan/repayment/history/unapprove, allowed only within 10 minutes and only by an admin (BE-19).
Reject: no Undo. Rejecting reverses the payment's allocations off the schedule and the advance balance, and re-applying that isn't safe to do automatically. So Reject keeps a confirmation sheet ("Reject ₹1,150 from Kavita Rao? Reason…") and has no Undo.
Payments recorded by employees: no Undo. A wrong payment is fixed by the admin rejecting it, which already reverses it correctly.
Should the title and text come from the server? Yes, with codes for logic (recommended). Updates are installed by hand (sideloaded APKs), so wording that lives only in the app can't be fixed without a new release. The proposal:
• The server sends { code, title, message, params }. title and message are already in the user's language, because the app sends Accept-Language: hi|en and the backend looks the code up in its own locales/en.json / hi.json.
• The app shows the server text as-is, and uses code only for logic (for example SESSION_EXPIRED → go to login, PAY_DUPLICATE_TXN → highlight the transaction field).
• The app keeps its own translations only for problems where the server can't answer: no internet, timeout, server down.
• Fixing a typo or adding Marathi to server messages then needs no app update. This replaces the "app translates by code" idea in BE-12.
Fix: one toast host, drawn above everythingRemove all 39 <CustomToast /> copies. A single <ToastHost/> sits at the app root, inside the safe-area provider and above navigation. UX rules every screen follows

U-01 · Five tabs per roleAdmin: Home, Customers, Loans, Leads, More. Employee: Home, Collect, Customers, Leads, More.
U-02 · Back button on every screen that isn't a tabTabs have a big title and no back button. Every other screen has back, a title, and at most one action (⋯). Leaving a form with unsaved changes asks first.
U-03 · Compact floating actionsThe main action is a small rounded button floating at the bottom right, above the keyboard. There are no full-width bottom bars. Two actions sit side by side (Reject · Approve). Buttons inside sheets are the same size and right-aligned.
U-04 · Easy to tapTap targets are at least 44–48dp, even when a button looks smaller (it gets extra padding around it). Body text is 13–14sp, and layouts must survive 130% font scaling and Hindi text.
U-05 · Long lists: group and page, never cutEvery item stays reachable. Runs of the same status collapse into one row (the employee screen's existing pattern), and pages load as you scroll. Nothing loads 200 rows at once, and nothing is hidden behind "top 3".
U-06 · Loading, empty and error statesPlaceholder rows while loading, a helpful empty message, and plain-language errors with Retry. Pull to refresh on every list.
U-07 · FormsLabels above fields, the right keyboard for each field, errors under the field. Chips when there are 7 or fewer options, a picker sheet for longer lists (for example 22 durations). Steps when there are more than about 8 fields.
U-08 · Money and destructive actionsConfirm with the amount and the name shown. The button is disabled while the request runs (the server also rejects duplicate transaction IDs). Then a clear success message.
U-09 · One status languageOne map (F-5) for all 5 status sets. Always colour plus text.
U-10 · Weak networks15-second timeout, an offline banner, and cached lists that show when they were saved. Payments are never retried automatically.
U-11 · Numbers and dates₹18,40,000 grouping, "26 Sep 2026", fixed-width digits so columns line up. All formatted for the chosen language.
U-12 · Readable in both modesWCAG AA contrast in every palette, light and dark. Every icon has a label for screen readers.
U-13 · Each role only sees what it can doDecided by can() (F-6). Nothing is shown that the server would reject, which is the cause of B-3, B-4 and B-5 today.
